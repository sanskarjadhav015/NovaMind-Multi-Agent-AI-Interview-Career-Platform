SECTION 1: ARCHITECTURE & MICROSERVICES DESIGN QUESTIONS
================================================================================

Q1. Why did you choose a Microservices architecture instead of a Modular Monolith?
--------------------------------------------------------------------------------
COUNTER-QUESTION FOLLOW-UP:
"Microservices introduce operational overhead, distributed logging complexity, 
and network latency. For an interview prep platform, isn't a monolith simpler?"

ANSWER:
"While a monolith is simpler to deploy initially, NovaMind has fundamentally 
divergent workload characteristics across its core domains:

1. Asymmetrical Resource Scaling:
   - The 'Interview Service' and 'Roadmap Service' are heavily I/O-bound and 
     dependent on external LLM inference, LangGraph graph compilation, and third-party 
     APIs (YouTube, Groq, Gemini). A spike in concurrent mock interviews can consume 
     substantial network sockets and thread pools.
   - The 'Auth Service' and 'Billing Service' are lightweight, high-security transactional 
     services with strict low-latency requirements (sub-50ms).
   - The 'Resume Service' handles bursty binary file uploads and CPU-bound text 
     parsing with pdf-parse and Multer.
   Decoupling them allows us to independently scale the Interview service pods to 
   20 replicas on AWS ECS during hiring seasons without over-provisioning Auth or 
   Billing pods.

2. Fault Domain Isolation:
   If an external LLM provider experiences elevated latency or a 504 Gateway 
   Timeout in the Interview Service, the candidate can still log in, review past 
   reports, build resumes, or buy coin packs without the entire application crashing.

3. Independent CI/CD & Deployability:
   We can update the LangGraph interview prompt graphs or ATS rubrics in the 
   Interview/Resume services and deploy them independently without risking 
   downtime or regression in the payment checkout pipeline."

--------------------------------------------------------------------------------
Q2. What is the role of your API Gateway, and why not let the frontend talk 
    directly to the microservices?
--------------------------------------------------------------------------------
ANSWER:
"Our API Gateway (running on port 8000 using express-http-proxy) serves four 
critical architectural purposes:

1. Unified Entry Point & Single CORS Policy:
   The client only communicates with `api.novamind.com`. We avoid exposing internal 
   microservice ports (6001-6005) or dealing with complex multi-origin CORS preflight 
   handshakes across multiple domains.

2. Centralized Authentication & Header Decoration:
   Instead of every single microservice repeating cookie parsing, session extraction, 
   and Redis queries, the Gateway's `isAuth` middleware validates the `session` cookie 
   once against Redis. It then enriches the forwarded request with an internal 
   trusted header (`x-user-id`). Internal services only need to read `req.headers['x-user-id']`, 
   eliminating redundant network trips to Redis.

3. Zero Trust Internal Security:
   Internal services run within a private AWS VPC subnet with no public IP addresses. 
   Only the Gateway is exposed to the Application Load Balancer.

4. Multipart Stream Preservation:
   In our Gateway's `proxyWithHeaders` utility, we explicitly configured 
   `parseReqBody: (srcReq) => !contentType.includes('multipart/form-data')`. This ensures 
   large PDF uploads stream directly through to the Resume service without the 
   Gateway attempting to parse the body into memory, which would corrupt binary 
   boundary headers and waste Gateway RAM."

--------------------------------------------------------------------------------
Q3. What happens if your Redis instance crashes? How does your system recover?
--------------------------------------------------------------------------------
ANSWER:
"We designed Redis interaction to be resilient and fail-safe:

1. Non-Blocking Reconnection Strategy:
   In `backend/shared/redis/redis.js`, we configured ioredis with:
   - `maxRetriesPerRequest: null`: Prevents request abort crashes during transient disconnects.
   - `retryStrategy: (times) => Math.min(times * 100, 3000)`: Implements exponential 
     backoff capped at 3 seconds to avoid hammering a recovering Redis node.

2. Safe Redis Fallback Wrappers:
   In our microservice controllers (e.g., `interview.controller.js` and `roadmap.controller.js`), 
   we wrapped all Redis operations in defensive try/catch helpers (`safeRedisGet`, 
   `safeRedisSet`, `safeRedisDel`). If Redis is down, these methods return `null` or 
   log a warning rather than throwing uncaught exceptions. The controllers seamlessly 
   fall back to fetching directly from MongoDB.

3. Production High Availability:
   In production AWS deployment, we deploy AWS ElastiCache for Redis with Multi-AZ 
   replication and automatic failover enabled, ensuring 99.99% uptime."

SECTION 2: AUTHENTICATION, SESSION MANAGEMENT & SECURITY QUESTIONS
================================================================================

Q4. Why did you use server-side Redis sessions instead of pure stateless JWTs 
    stored in LocalStorage or cookies?
--------------------------------------------------------------------------------
COUNTER-QUESTION FOLLOW-UP:
"Stateless JWTs eliminate the Redis lookup entirely and scale infinitely. Why 
introduce Redis state for sessions?"

ANSWER:
"While stateless JWTs sound convenient, they have severe security and business 
drawbacks in a commercial SaaS application:

1. Inability to Revoke Compromised Sessions Instantly:
   With pure stateless JWTs, once a token is signed and issued, it remains valid 
   until expiration. If a candidate logs out, changes credentials, or suspects an 
   account compromise, there is no way to invalidate the token immediately without 
   maintaining a distributed token blacklist—which effectively reintroduces state! 
   With Redis sessions, `redis.del('session:' + sessionId)` immediately revokes 
   access across all devices.

2. Real-Time Balance Synchronization:
   In NovaMind, interview coins change constantly as users practice interviews 
   (-50 coins), scan resumes (-10 coins), or purchase packs (+900 coins). Storing 
   coin balance inside a stateless JWT causes stale balance displays unless tokens 
   are constantly re-issued. By caching user session state in Redis with a 7-day 
   TTL, we achieve instant updates across all browser tabs without extra database hits.

3. XSS Protection:
   Stateless tokens stored in browser `localStorage` are vulnerable to Cross-Site 
   Scripting (XSS) extraction. Our session ID is stored in an `HttpOnly`, `Secure`, 
   `SameSite=Lax/None` cookie, preventing JavaScript from ever reading it."

--------------------------------------------------------------------------------
Q5. How do you prevent CSRF (Cross-Site Request Forgery) attacks on session cookies?
--------------------------------------------------------------------------------
ANSWER:
"We employ a defense-in-depth approach:
1. `SameSite=Lax` in development and `SameSite=None; Secure` with strict HTTPS in 
   production.
2. The Gateway enforces strict CORS origin whitelisting:
   ```js
   const allowedOrigins = [process.env.FRONTEND_URL, 'http://localhost:5173'];
   ```
   Requests originating from untrusted third-party domains are rejected at the 
   preflight (OPTIONS) handshake before touching any controller.
3. State-changing requests (like starting interviews, submitting answers, and 
   charging coins) are restricted to POST/PUT methods with JSON or multipart payloads."

SECTION 3: AI ENGINEERING, MULTI-AGENT ORCHESTRATION & LANGGRAPH QUESTIONS
================================================================================

Q6. Why did you use LangGraph instead of standard LangChain chains or sequential 
    prompts?
--------------------------------------------------------------------------------
COUNTER-QUESTION FOLLOW-UP:
"Isn't LangGraph overly complex for just asking 6 interview questions?"

ANSWER:
"LangGraph was chosen specifically because real interviews are NOT static, linear 
prompt chains—they are cyclic state machines that require conditional routing, 
state retention, and branching logic:

1. Dynamic Branching & Conditional Routing:
   In `backend/services/interview/graph/graph.js`:
   - At `START`, the router inspects `state.action`:
     - If `action === 'start'`, it routes to `interviewAgent` to synthesize role-tailored questions and immediately terminates at `END`.
     - If `action === 'feedback'`, it routes to `feedbackAgent` to score the current question.
   - After `feedbackAgent`, `feedbackRouter` evaluates `state.completed`:
     - If `completed === false` (candidate still has remaining questions), it terminates the turn at `END` and returns the next question.
     - If `completed === true` (last question answered), it conditionally transitions to `summaryAgent` to compile the final performance radar and executive report before reaching `END`.

2. Structured State Retention (`InterviewState`):
   LangGraph maintains a typed `Annotation.Root` encapsulating the entire candidate 
   state: `questions`, `currentQuestion`, `userAnswer`, `difficulty`, `feedback`, 
   and `report`. This guarantees data integrity between nodes without messy global 
   variables or manual object passing.

3. Reusability in Roadmap Generation:
   We used the same architectural pattern in the Roadmap Service (`RoadmapState`): 
   `roadmapAgent` creates the curriculum modules, and passes state directly to 
   `resourceAgent`, which attaches YouTube links and official documentation."

--------------------------------------------------------------------------------
Q7. How do you handle LLM latency, rate limits, and provider outages?
--------------------------------------------------------------------------------
ANSWER:
"In `backend/services/interview/config/llm.js`, we engineered a 3-Tier Native 
LangChain Fallback Pipeline:

```js
const llm = groqLlm.withFallbacks([openRouterLlm, geminiLlm]);
```

1. Tier 1 (Primary - Groq):
   - Model: `openai/gpt-oss-120b` running on Groq LPUs.
   - Why: Extremely low Time-To-First-Token (sub-400ms). Crucial for live mock 
     interviews where waiting 10 seconds for an AI response ruins the conversational illusion.
2. Tier 2 (First Fallback - OpenRouter):
   - Model: `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free`.
   - Why: If Groq experiences rate limiting (HTTP 429) or token capacity exhaustion, 
     LangChain instantly catches the error and redirects the prompt to OpenRouter.
3. Tier 3 (Second Fallback - Google Gemini):
   - Model: `gemini-3.6-flash`.
   - Why: Highly reliable global cloud inference with a large context window."

Q8. How do you prevent LLM hallucination and ensure reliable JSON parsing?
--------------------------------------------------------------------------------
COUNTER-QUESTION FOLLOW-UP:
"LLMs frequently return conversational filler like 'Here is your JSON:' or wrap 
responses in markdown code fences. What happens when JSON.parse() crashes?"

ANSWER:
"We implemented a multi-layered sanitization pipeline across all agents:

1. Prompt Hardening:
   Prompts explicitly enforce:
   - 'Return ONLY valid JSON.'
   - 'Do NOT use markdown.'
   - 'Do NOT explain anything.'
   - Provide an exact JSON structural schema in the prompt with empty keys.

2. Reasoning Tag & Markdown Fence Stripping:
   Modern reasoning models (like DeepSeek, Nemotron) often include internal `<think>` 
   deliberations. In our parsing functions:
   ```js
   let text = content
     .replace(/<think>[\s\S]*?<\/think>/g, '') // Strip reasoning tags
     .trim();
   const match = text.match(/```(?:json)?\s*([\s\S]*?)\s*```/i);
   if (match && match[1]) {
     text = match[1].trim();
   } else {
     text = text.replace(/```json/gi, '').replace(/```/g, '').trim();
   }
   ```

3. Bracket Isolation:
   We extract from `indexOf('{')` to `lastIndexOf('}')` to ignore any preamble or postamble text.

4. Non-Printable Unicode & Control Character Cleansing:
   In `resume.controller.js`:
   ```js
   cleanJson = cleanJson.replace(/[\u0000-\u001F]+/g, (match) =>
     match === '\n' || match === '\r' || match === '\t' ? ' ' : ''
   );
   ```
   This prevents `SyntaxError: Bad control character in string literal` when candidates 
   have strange PDF glyphs."

SECTION 4: DATABASE, CONCURRENCY & PAYMENT PROCESSING QUESTIONS
================================================================================

Q9. How do you prevent race conditions and negative coin balances when users 
    trigger multiple interview or scan requests simultaneously?
--------------------------------------------------------------------------------
ANSWER:
"A classic junior mistake is doing a 'Read-Modify-Write' pattern:
```js
// INSECURE (Vulnerable to Race Conditions):
const user = await User.findById(userId);
if (user.interviewCoin >= 50) {
  user.interviewCoin -= 50;
  await user.save();
}
```
If two requests arrive simultaneously, both read 50 coins, and both decrement, 
resulting in 0 coins instead of 1 failing.

In `backend/services/auth/controllers/auth.controller.js` (`useCoins`), we implemented 
an Atomic Conditional Update:
```js
const user = await User.findOneAndUpdate(
  { _id: sessionData.userId, interviewCoin: { $gte: coinAmount } },
  { $inc: { interviewCoin: -coinAmount } },
  { returnDocument: 'after' }
);
```
Why this is 100% thread-safe:
- MongoDB handles this operation with document-level locking.
- The decrement `{ $inc: { interviewCoin: -coinAmount } }` only executes if the 
  filter condition `{ interviewCoin: { $gte: coinAmount } }` evaluates to true.
- If the balance is insufficient, MongoDB returns `null`, and we return an HTTP 
  403 Forbidden with `{ message: 'Not enough interview coins' }`."

Q10. How does your Razorpay payment verification work, and how do you ensure 
     idempotency?
--------------------------------------------------------------------------------
ANSWER:
"In `backend/services/billing/controllers/billing.controller.js`:

1. Order Creation:
   - When a user chooses a plan, we calculate the amount in paise (`plan.amount * 100`).
   - We create an order via Razorpay SDK and store a pending billing record with `status: 'created'`.

2. HMAC SHA-256 Verification:
   - Upon payment, Razorpay sends back `razorpay_order_id`, `razorpay_payment_id`, 
     and `razorpay_signature`.
   - We generate the cryptographic signature on our backend using Node's native `crypto` module:
     ```js
     const genSign = crypto
       .createHmac('sha256', process.env.RAZORPAY_KEY_SECRET)
       .update(`${orderId}|${paymentId}`)
       .digest('hex');
     ```
   - If `genSign !== signature`, someone attempted to forge payment parameters. 
     We mark status as `failed` and reject with HTTP 400.

3. Idempotency Guarantee:
   - If Razorpay triggers a webhook retry or a user refreshes the payment page, 
     we check:
     ```js
     if (payment.status === 'paid') {
       return res.status(200).json({ success: true, message: 'Payment already verified' });
     }
     ```
   - This guarantees that coins are never credited twice for the same transaction."

SECTION 5: HIGH-VOLUME FILE INGESTION & STREAMING QUESTIONS
================================================================================

Q11. How do you handle resume PDF uploads without causing memory leaks or 
     blocking the Node.js event loop?
--------------------------------------------------------------------------------
ANSWER:
"In `backend/services/resume`:
1. Gateway Streaming:
   As mentioned earlier, the API Gateway does not buffer multipart requests into 
   memory. It pipes the raw HTTP binary stream directly to the Resume microservice.

2. Disk Storage with File Filter:
   Multer is configured with `multer.diskStorage` to stream the file to a temporary 
   directory (`./uploads`) with unique timestamped filenames. We apply strict constraints:
   - `fileSize: 20 * 1024 * 1024` (20MB upper limit).
   - `fileFilter: (req, file, cb) => file.mimetype === 'application/pdf'`.

3. Synchronous Post-Processing Cleanup:
   Once `pdf-parse` extracts the text buffer, we immediately clean up the file using 
   `fs.unlinkSync(file.path)` inside both the `try` block and the `catch` block. 
   This guarantees that temporary upload files never accumulate on the container's 
   ephemeral disk."

Q12. How does real-time speech-to-text work in your interview simulation?
--------------------------------------------------------------------------------
ANSWER:
"In `Step2interview.jsx`, we leverage the browser's native `webkitSpeechRecognition` 
/ `SpeechRecognition` API (Web Speech API):

1. Continuous Listening & Interim Results:
   - We set `recognition.continuous = true` and `recognition.interimResults = true`.
   - As the candidate speaks, interim hypotheses are streamed to a live subtitle 
     badge (`setLiveInterim(interimTranscript)`), providing immediate visual feedback.
   - Finalized speech chunks are appended to the accumulated answer state:
     `setAnswer((prev) => prev + finalChunk)`.

2. Hybrid Input Model (Voice + Code):
   - Speech recognition and live code editing work seamlessly together.
   - If a candidate explains their algorithm verbally and then clicks 'Open Live Coding Pad', 
     they can type or insert code templates in Python, JS, C++, etc.
   - The inserted code block is appended to the transcript wrapped in markdown fences, 
     allowing the candidate to speak their thought process while coding."

Q13. How did you optimize frontend performance in React 19?
--------------------------------------------------------------------------------
ANSWER:
1. Dynamic Route Splitting & Lazy Rendering:
   Routes are isolated using React Router v7 and conditional rendering.
2. Memoized State Transitions:
   Framer Motion animations utilize GPU-accelerated transforms (`transform`, `opacity`) 
   to maintain 60 FPS transitions during avatar video playback and modal renders.
3. Production Bundle Optimization:
   Our Vite build transforms 1,116 modules and outputs gzip-compressed chunks 
   (~323kB for main vendor bundle) in just 2.2 seconds.
4. Redux Slicing:
   We used Redux Toolkit specifically for complex resume form state where child 
   components (ATS Template, Modern Template, Tech Template) need reactive access 
   to nested skill and project arrays without causing root re-renders."

SECTION 7: TRICKY ENGINEERING COUNTER-QUESTIONS & "HARDEST BUG" SCENARIOS
================================================================================

Q14. "What was the most challenging technical bug you encountered in this project, 
     and how did you debug and resolve it?"
--------------------------------------------------------------------------------
ANSWER (Senior-Level Narrative):
"One of the subtlest and most critical bugs was in the interview submission endpoint 
and LLM response parsing:

1. The Condition Bug:
   In `interview.controller.js`, the validation check was originally written as:
   `if (!interviewId && !answer)`.
   Because of the logical AND (`&&`), if a client request contained an `interviewId` 
   but an empty or undefined `answer`, `!interviewId` evaluated to `false`, causing 
   the entire check to pass! The controller proceeded to invoke LangGraph with an 
   undefined answer, which caused downstream LLM prompt rendering errors.
   -> Resolution: Corrected the condition to `if (!interviewId || !answer)` and added 
      strict payload validation.

2. The Reasoning Model JSON Parsing Bug:
   When switching to modern open reasoning LLMs (like Nemotron and DeepSeek models), 
   the agents began failing sporadically with `SyntaxError: Unexpected token < in JSON`. 
   Upon deep inspection of raw network outputs, we realized the model was returning 
   internal chain-of-thought traces wrapped in `<think>...</think>` tags before 
   outputting the JSON.
   -> Resolution: We implemented a regex pre-sanitizer:
      `content.replace(/<think>[\s\S]*?<\/think>/g, '').trim()`, followed by greedy 
      brace boundary extraction (`indexOf('{')` to `lastIndexOf('}')`). This made our 
      JSON ingestion completely resilient across any LLM."

Q15. "If 100,000 users took mock interviews simultaneously tomorrow, what would 
     break first, and how would you redesign the system?"
--------------------------------------------------------------------------------
ANSWER:
"Under 100k concurrent interviews, the first bottleneck would be **Synchronous LLM 
Inference Latency and HTTP Connection Exhaustion**:

Current Bottleneck:
- A candidate submits an answer -> an HTTP connection is held open while LangGraph 
  invokes the LLM, awaits evaluation, and optionally generates a summary report. 
- LLM inference takes 1-3 seconds. Holding 100k Express connections open would 
  exhaust Node's socket descriptors and memory limits.

Redesign for 100k Scale:
1. Asynchronous Event-Driven Architecture (Message Queue):
   - Replace direct HTTP graph invocation with an asynchronous queue using Apache 
     Kafka or AWS SQS + BullMQ on Redis.
   - When a candidate submits an answer, the Gateway returns HTTP 202 Accepted with 
     a `jobId` immediately (< 10ms).
2. Worker Pool & WebSockets:
   - A dedicated fleet of Python/Node worker pods consume jobs from the queue and 
     execute the LangGraph agents.
   - Workers stream evaluation feedback back to the client in real-time over WebSockets 
     (Socket.io / AWS API Gateway WebSocket).
3. LLM Provisioning & Caching:
   - Switch from public pay-per-token API endpoints to dedicated throughput instances 
     (e.g., AWS Bedrock provisioned throughput or self-hosted vLLM on Kubernetes with 
     Nvidia H100 GPUs).
   - Implement semantic caching using Redis vector similarity: if common questions 
     (e.g., 'Explain Big-O of QuickSort') receive semantically identical answers, 
     serve pre-computed evaluations without invoking the LLM."
